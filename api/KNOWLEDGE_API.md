## 1. Принципи

- **Minerva — джерело правди.** Тут зберігаються листи, вкладення, клієнти, проєкти, права й налаштування того, що можна індексувати.
- **RAG — відновлюваний пошуковий індекс.** Qdrant можна в будь-який момент перебудувати з Minerva.
- **Зв'язок лише через HTTP API.** RAG не має доступу до PostgreSQL чи файлів Minerva.
- **Модель pull.** RAG сам забирає зміни зі стрічки Minerva. Якщо RAG вимкнений, у Minerva нічого не губиться: зміни накопичуються, і RAG їх добирає, коли повернеться. Minerva не залежить від того, чи RAG доступний.
- **Обсяг індексації вмикає людина в Minerva.** Сторінка «База знань» задає скриньки, період, категорії й вкладення. Поки індексацію не ввімкнено, стрічка порожня. RAG нічого не індексує «сам».
- **Вектори створюються локально на ПК RAG** (EmbeddingGemma). Під час індексації текст листів у хмару не передається.
- **Текст листів і вкладень — це дані, а не інструкції.**

```
Minerva (NAS)                                       RAG (ПК 192.168.2.68)
  листи / проєкти ──► журнал змін (seq)
                         │  GET /api/v1/knowledge/changes/?after=N   ◄── воркер індексації (pull)
                         │  GET …/attachments/{i}/                   ◄── завантаження вкладень
                         │  POST /api/v1/knowledge/status/           ◄── звіт: indexed / failed
  «База знань»: прогрес, помилки  ◄──────────────────────────────────┘
  помічник у пошті ──► POST {RAG}/v1/private/search  ──► Qdrant crm_correspondence
       (фільтри доступу ставить Minerva; результат Minerva ще раз перевіряє)
```

## 2. Доступ

### 2.1 RAG → Minerva

- Заголовок `Authorization: Token <ключ>`, де ключ — це окремий `APIKey` у Minerva, наприклад з назвою `rag-knowledge`.
- Нові права (scopes):
  - `knowledge:read` — читання стрічки, документів, вкладень і маніфесту;
  - `knowledge:write` — надсилання статусів індексації.
- Ключ, прив'язаний до магазину (`APIKey.shop`), отримує `403` на всі маршрути `/knowledge/`. Ключ магазину ніколи не має цих прав.
- Відкликати доступ можна в адмінці Minerva: зняти «Активний» з ключа.

### 2.2 Minerva → RAG (приватний пошук)

- Окремий ключ RAG (`Authorization: Bearer <private key>`), відмінний від ключа магазину й вебпроксі.
- Маршрути `/v1/private/*` недоступні через публічний вебміст (:8790) і з боку магазину.
- Ключ зберігається лише на сервері Minerva (`RagSettings`), у браузер не потрапляє.

## 3. Ідентифікатори й версії

| Поле | Формат | Опис |
|---|---|---|
| `doc_id` | `email:<pk>` | Лист Minerva. Пізніше додадуться `project:<pk>` (опис проєкту) і `offer:<pk>` (надіслана ревізія Angebot). |
| `version` | `sha256:<hex>` | Хеш полів, що індексуються: тексту, адрес, дати, клієнта, проєктів, замовлень, категорії, вкладень і доступу. Якщо змінилась прив'язка до проєкту або доступ — змінюється й версія. |
| `seq` | ціле, зростає | Номер запису в журналі змін Minerva. RAG зберігає останній оброблений `seq` як курсор. |

**Ідемпотентність.** Повтор `upsert` з тією самою `version` нічого не змінює. Новий `upsert` того самого `doc_id` замінює всі фрагменти попередньої версії.

## 4. Маршрути Minerva (`/api/v1/knowledge/`)

### 4.1 `GET /changes/?after=<seq>&limit=<1..200>`

Повертає зміни після курсора в порядку зростання `seq`. Без `after` починає з початку журналу. `limit` за замовчуванням 50.

```json
{
  "items": [
    {"seq": 1042, "doc_id": "email:5531", "action": "upsert", "changed_at": "2026-10-20T08:15:02Z",
     "document": { "...": "див. 5. Документ email" }},
    {"seq": 1043, "doc_id": "email:77", "action": "delete", "changed_at": "2026-10-20T08:16:40Z"}
  ],
  "next_after": 1043,
  "has_more": true
}
```

- `action`:
  - `upsert` — документ з поточним станом на момент читання;
  - `delete` — прибрати всі фрагменти `doc_id` з індексу.
- Причини `delete`: лист видалено, перенесено в спам чи кошик, виключено з бази знань, звужено налаштування (скринька, період, категорія) або змінено доступ так, що лист більше не підлягає індексації.
- Якщо на момент читання документ уже не відповідає налаштуванням, Minerva віддає `delete` замість `upsert`.
- В одній сторінці кожен `doc_id` трапляється не більше одного разу: залишається останній стан. Між сторінками повтори можливі, тому RAG має бути ідемпотентним.
- Якщо курсор старший за найдавніший збережений запис журналу, повертається `410 {"error": "cursor_expired", "oldest_seq": N}`. Тоді RAG робить звірку через маніфест (4.4) і продовжує з `oldest_seq`.

### 4.2 `GET /documents/<doc_id>/`

Поточний документ у тій самій схемі, що й у стрічці.
- `404` — документа немає або він більше не підлягає індексації. RAG видаляє його з індексу.

### 4.3 `GET /documents/<doc_id>/attachments/<index>/`

Повертає файл вкладення з його `Content-Type`.
- Доступно лише для вкладень із `"indexable": true` (рішення приймає налаштування Minerva: типи й максимальний розмір).
- Інакше `404`.

### 4.4 `GET /manifest/?type=email&after_id=<pk>&limit=<1..5000>`

Повний перелік документів, які зараз мають бути в індексі: `[{"doc_id", "version"}]`, плюс `next_after_id` і `has_more`.
- Потрібен для звірки після `410`, після перебудови Qdrant або раз на добу.
- Документи, яких немає в маніфесті, RAG видаляє.

### 4.5 `POST /status/` (потрібно `knowledge:write`)

```json
{"items": [
  {"doc_id": "email:5531", "version": "sha256:…", "state": "indexed", "chunks": 4,
   "attachments_indexed": 1, "indexed_at": "2026-10-20T08:15:09Z"},
  {"doc_id": "email:5532", "version": "sha256:…", "state": "failed", "error": "pdf: no text layer"},
  {"doc_id": "email:77", "state": "deleted"}
]}
```

- До 200 записів за раз.
- `state`:
  - `indexed`;
  - `failed`;
  - `skipped` — порожній текст або непідтримуваний формат;
  - `deleted`.
- Відповідь: `{"accepted": N, "stale": M}`. `stale` — це записи з версією, яка вже неактуальна. Їх ігноровано, бо прийде новий `upsert`.
- За цими статусами Minerva показує прогрес («Оброблено 320 із 1500»), помилки й час останньої синхронізації. Для цього Minerva не потрібно звертатися до RAG.

### 4.6 `GET /summary/`

```json
{"enabled": true, "eligible": 1500, "last_seq": 10432, "indexed": 320, "failed": 3, "pending": 1177,
 "settings_version": 7}
```

`settings_version` змінюється, коли змінюються налаштування бази знань. Це інформаційне поле: відповідні `delete`/`upsert` уже є в стрічці.

### 4.7 Коди помилок

| Код | Значення | Дія RAG |
|---|---|---|
| 401 | немає ключа або ключ неправильний | зупинити синхронізацію, показати помилку, не повторювати в циклі |
| 403 | немає права `knowledge:*` або ключ магазину | так само |
| 404 | документа або вкладення немає | видалити з індексу |
| 410 | курсор застарів | звірка через маніфест |
| 429 | ліміт запитів | пауза з `Retry-After` |
| 5xx / тайм-аут | Minerva недоступна | повтор із наростаючою паузою (30 с → 10 хв); курсор не зсувати |

## 5. Документ `email`

```json
{
  "doc_id": "email:5531",
  "type": "email",
  "version": "sha256:9f…",
  "url": "https://minerva.example/email/message/5531/",
  "mailbox": {"id": 1, "address": "sales@minerva.example"},
  "thread": {"id": 812, "subject": "RE: Order 100200"},
  "message_id": "<abc@client.example>",
  "in_reply_to": "<prev@minerva.example>",
  "direction": "in",
  "category": "customer",
  "sent_at": "2026-10-02T09:00:00Z",
  "subject": "RE: Order 100200",
  "from": {"email": "buyer@client.example", "name": "Alex Buyer"},
  "to": ["sales@minerva.example"],
  "cc": ["purchasing@client.example"],
  "text": "повний текст листа (до 100 000 символів)",
  "text_new": "лише нова частина: без цитованої історії та підпису (до 20 000 символів)",
  "customer": {"id": 15, "name": "Client GmbH"},
  "projects": [{"id": 3, "code": "P-2026-003", "name": "Antennen Client"}],
  "orders": [{"id": 77, "number": "shop:100200"}],
  "attachments": [
    {"index": 0, "name": "Invoice_100200.pdf", "content_type": "application/pdf",
     "size": 48211, "indexable": true,
     "url": "/api/v1/knowledge/documents/email:5531/attachments/0/"}
  ],
  "access": {"scope": "mailbox", "mailbox_id": 1, "user_ids": [1]}
}
```

- `direction`:
  - `in` — від зовнішнього співрозмовника;
  - `out` — від нас назовні;
  - `internal` — між власними адресами, наприклад внутрішнє пересилання.
- `text_new` — основний текст для векторів. Цитати попередніх листів уже проіндексовані як окремі листи, тож повторювати їх не треба. `text` потрібен для показу й контролю.
- `customer`, `projects` і `orders` можуть бути порожніми. Це поточні зв'язки Minerva: їх може виправити людина, тоді прийде нова версія.
- `access` — хто в Minerva бачить лист. RAG зберігає ці поля в payload і зобов'язаний фільтрувати за ними в приватному пошуку.

## 6. Маршрути RAG для Minerva (`/v1/private/`)

### 6.1 `POST /v1/private/search`

Синхронний гібридний пошук: точний збіг артикулів, номерів і адрес плюс векторний пошук і ранкер. **Без генерації LLM.** Текст відповіді складає Minerva своєю моделлю.

```json
{
  "query": "що ми обіцяли клієнту щодо строків поставки антен",
  "types": ["email"],
  "filters": {
    "mailbox_ids": [1],
    "user_id": 1,
    "customer_id": 15,
    "project_id": null,
    "exclude_thread_ids": [812],
    "since": "2025-01-01"
  },
  "limit": 8
}
```

- `filters.mailbox_ids` і `filters.user_id` **обов'язкові**. Без них відповідь — `400`.
  - Їх визначає сервер Minerva з прав користувача.
  - LLM ці значення не задає.
- Решта фільтрів необов'язкова.
- `exclude_thread_ids` — щоб не повертати поточну гілку, яку Minerva вже має локально.

Відповідь `200`:

```json
{
  "hits": [
    {"doc_id": "email:4410", "chunk": 1, "score": 0.81, "text": "…фрагмент…",
     "subject": "AW: Lieferzeit Antennen", "sent_at": "2026-06-11T14:02:00Z",
     "from_email": "buyer@client.example", "thread_id": 640,
     "attachment": null}
  ],
  "took_ms": 140,
  "index": {"docs": 1500, "last_seq": 10432, "embedding_model": "embeddinggemma"}
}
```

- Запит триває не довше 10 с.
  - `429` — зайнято, повторити пізніше.
  - `503` — Qdrant або embedding недоступні.
- Пошук не повинен чекати на єдиний слот LLM із `/v1/ask`.
- `attachment`, якщо фрагмент із вкладення: `{"index": 0, "name": "…"}`.
- Minerva перевіряє кожен `doc_id` за своїми правами, перш ніж показати фрагмент чи передати його в AI. Неналежні фрагменти відкидаються.

### 6.2 `GET /v1/private/health`

```json
{"status": "ok", "sync": {"enabled": true, "last_seq": 10432, "last_run_at": "…", "last_error": null,
 "backlog_hint": 0}, "index": {"docs": 1500, "chunks": 5210, "embedding_model": "embeddinggemma"}}
```

Minerva викликає цей маршрут лише зі сторінки «База знань» і при діях помічника, з тайм-аутом 3 с. На відкриття кожної сторінки виклику немає.

## 7. Поведінка, коли RAG недоступний

- **Пошта, CRM, проєкти, Angebote й AI-відповіді працюють без RAG.**
- Помічник пише: «RAG недоступний. Працюємо з даними Minerva; пошук у додатковій історії не виконано».
- Після кількох помилок поспіль Minerva на 5 хвилин перестає звертатися до RAG (запобіжник). Користувач може примусово спробувати знову.
- Індексація просто чекає: стрічка накопичує зміни, RAG добирає їх після відновлення.

## 8. Що свідомо не входить у v1

- Генерація відповідей на RAG для приватних даних (лише пошук).
- Індексація `project:*` і `offer:*` — схема буде додана, коли з'являться ці модулі.
- OCR сканів у вкладеннях.
