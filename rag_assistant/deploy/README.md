# Робочий приватний RAG: з'єднання NAS ↔ RAG-ПК

База знань пошти (`/api/v1/knowledge/` + пошук `/v2`) працює через окремий **приватний RAG** на RAG-ПК.
Він не має нічого спільного з публічним RAG продукції (`app.sevskiy.com` → 8787) і чатом (`ai.sevskiy.com`).

```
Minerva (Docker на NAS) ──► <шлюз Docker-мережі>:18789 ═══ SSH ═══► RAG-ПК 127.0.0.1:8789  (приватний RAG)
RAG-ПК 127.0.0.1:18081  ═══ SSH ═══► NAS 127.0.0.1:8000  (Minerva: стрічка листів для індексації)
```

- Тунель відкриває NAS (`nas_rag_tunnel.sh`). В інтернет і в локальну мережу нічого не відкривається: усі порти прив'язані
  до `127.0.0.1` або до шлюзу Docker-мережі Minerva.
- SSH-ключ тунелю дозволяє лише ці два перенаправлення портів — без входу в систему й без команд.
- Приватний RAG сам вимагає, щоб його слухали лише на `127.0.0.1`, а до Minerva він звертався через HTTPS або `127.0.0.1`.
  Тунель задовольняє обидві умови без сертифікатів.

## Що вже стоїть на RAG-ПК (192.168.2.68)

| Що | Де |
|---|---|
| Приватний RAG `sevskiy-prod` | `D:\RAG-private-prod` (там же `README.txt`), слухає `127.0.0.1:8789` |
| Автозапуск | задача Windows `Minerva-Private-RAG` при вході користувача `user` → `launcher.py` (перезапуск після збою) |
| Індекс | Qdrant `minerva-rag-prod-qdrant` (`127.0.0.1:16334`, з API-ключем), колекція `crm_correspondence` |
| Embeddings / reranker | Ollama `embeddinggemma`; reranker у контейнері `open-webui` (як у тестовій копії) |
| Ключі й стан | `D:\RAG-private-prod\data` — доступ лише `user` і SYSTEM |
| Журнали | `D:\RAG-private-prod\logs\launcher.log`, `runtime.log` |

Тестова копія (`D:\RAG-private-e2e`, 8788), публічний RAG (8787) і чат (8790) від неї не залежать.

## Підключення — по кроках

1. **NAS** (`ssh admin@192.168.2.123`):
   ```sh
   cd /volume1/docker/tabele_mvp && sudo sh rag_assistant/deploy/nas_rag_tunnel.sh setup
   ```
   Скрипт створить ключ тунелю в `/volume1/docker/rag-tunnel` (поза репозиторієм) і перевірить відбиток SSH-ключа RAG-ПК.
   Наприкінці він надрукує один рядок `Add-Content …`.
2. **RAG-ПК**: відкрийте PowerShell «від імені адміністратора» і вставте цей рядок. Він додає ключ NAS у
   `C:\ProgramData\ssh\administrators_authorized_keys` з обмеженнями.
3. **NAS**:
   ```sh
   sudo sh rag_assistant/deploy/nas_rag_tunnel.sh start
   ```
   Має з'явитися «Minerva → RAG: ✅» і адреса для Minerva.
4. **Автозапуск тунелю**:
   - DSM → Панель керування → Планувальник завдань → Створити → Завдання, яке запускається подією → Сценарій користувача;
   - користувач `root`, подія «Завантаження»;
   - сценарій: `sh /volume1/docker/tabele_mvp/rag_assistant/deploy/nas_rag_tunnel.sh start`.
5. **Minerva → «🧠 База знань»**, блок «Підключення RAG»:
   - «Назва цього сервера для RAG»: `sevskiy-prod`;
   - «Адреса RAG-ПК»: адреса з `status` (шлюз, напр. `172.18.0.1`);
   - «Порт»: `18789`;
   - «HTTPS»: вимкнено.

   У блоці «API-ключі», поле «API-ключ RAG (Minerva → RAG)» — вміст файлу `D:\RAG-private-prod\data\private-api-key.txt`.

   Збережіть. «Індексувати» поки не вмикайте.
6. **Ключ Minerva для RAG**:
   - «🔑 Створити ключ для RAG» → відкрийте створений ключ і скопіюйте його;
   - на RAG-ПК вставте його в `D:\RAG-private-prod\data\minerva-knowledge-key.txt` (Блокнот) і збережіть.

   Протягом ~30 с RAG запуститься: у `logs\launcher.log` з'явиться «RAG запущено».
7. **«🔌 Перевірити пошук RAG»** → має бути успіх.
8. **Пілот**:
   - у блоці «Що індексувати» увімкніть індексацію, виберіть одну скриньку й «з дати» за останні 30 днів;
   - стан видно на панелі «Стан».

   Масову індексацію архіву запускайте лише після перевірки пілоту.

## Обслуговування

- `sudo sh rag_assistant/deploy/nas_rag_tunnel.sh status` — стан тунелю, перевірка і що вписати в Minerva.
- Тунель сам перепідключається після обриву мережі чи перезавантаження RAG-ПК (журнал `/volume1/docker/rag-tunnel/tunnel.log`).
- Після `docker-compose down` + `up` шлюз Docker-мережі може змінитися. Тоді виконайте `restart` і, якщо адреса інша,
  оновіть «Адресу RAG-ПК» у Minerva.
- Новий ключ Minerva для RAG: вставте його в `minerva-knowledge-key.txt` — RAG перезапуститься сам. Старий ключ вимкніть у Minerva.
- Якщо RAG недоступний, Minerva працює далі без нього (запобіжник у `retrieval.py`).

## Чому не через `app.sevskiy.com`

`app.sevskiy.com` — публічна адреса в інтернеті, вона веде на публічний RAG продукції (8787).
Щоб пустити через неї `/v2`, довелося б:
- змінити публічний RAG (код Codex), щоб він пересилав `/v2` на приватний;
- виставити пошук по всій переписці в інтернет під захистом лише одного ключа.

До того ж зворотний напрямок (RAG → стрічка листів Minerva) цим не вирішується.

Порти тунелю (18789, 18081, 8789, 16334) — внутрішні: вони прив'язані до `127.0.0.1` або до шлюзу Docker-мережі, тож ззовні
їх не видно й у роутері чи зворотному проксі нічого відкривати не треба.
