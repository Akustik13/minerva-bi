## 📐 Архітектурні правила

1. **Django Admin як основний UI** — не писати окремий фронтенд
2. **Signals** для CRM ↔ Sales синхронізації — не дублювати логіку
3. **SHA256 external_key** — завжди при імпорті клієнтів
4. **affects_stock=True** — обов'язково для попадання в dashboard статистику
5. **Placeholder app pattern** (faq, ai, backup): `managed=False` + override `get_urls()`
6. **Sidebar групи** — змінювати тільки в `base_site.html` GROUPS масив
7. **Model order у sidebar** — `tabele/admin.py` → `model_order` dict у `_get_app_list()`
8. **Media:** `media/orders/{source}/{order_number}/` — структуру не змінювати
9. **RFM логіка** — тільки в `crm/utils.py`
10. **`user.has_perm("app.дія_модель")` = ролі Minerva** — `core/permissions.py` через `core.auth_backend.EmailOrUsernameBackend.has_perm` (стандартні права Django людям не призначаються): спершу групи / права Django, інакше — активний співробітник; superadmin / admin — усе; core / auth — лише правами Django; модуль доступний людині (реєстр, роль / пакет / ручний список, хуки модулів); не в `denied_models`; view — досить модуля, add / change / delete — операція (`get_allowed_operations`), delete — ще й `user_can(user, 'delete')`. У власних сторінках модулів перевіряти саме `has_perm`, а не `is_superuser`. Меню адмінки (`tabele/admin._get_app_list`) будується «як суперкористувач», потім лишає лише моделі з `has_view_permission` / `has_change_permission` людини (`_can_open`); `base_site.html` `_linkAllowed` ховає посилання на модель, якої немає в меню
11. **Ключі й паролі в адмінці** — `tabele/admin.py` (глобально для всіх ModelAdmin): поле-пароль (`PasswordInput`) ніколи не підставляє збережене (`render_change_form` → `_hide_secrets`: `render_value=False` + підказка `core.secrets.placeholder`); старі поля з `render_value=True` — порожнє при збереженні лишає збережене (`save_form`); поля «тільки читання» з назвами `SECRET_NAME_RE` (…password / secret / api_key / token / license_key / access_key …) — `core.secrets.mask`. Новий секрет у моделі — `PasswordInput(render_value=True)` у `get_form` (або своя форма з `render_value=False` і «Видалити збережений»), значення в HTML не виводити. ⚙️ Налаштування AI (`strategy.AISettingsAdmin`) — лише `is_minerva_admin`. «Ролі користувачів» (`core.UserProfileAdmin`): не-адміністратор (і без «Може керувати юзерами») — лише свій профіль, поля доступу (`ACCESS_FIELDS`, «Ручне перевизначення модулів») — тільки читання
12. **👁 Як бачить Minerva** (`/admin/core/userprofile/<pk профілю>/access/`, `UserProfileAdmin._access_view`, колонка `preview_link`, кнопка в картці; адміністратор / «Може керувати юзерами» — будь-кого, інші — себе; JSON `…/debug/` — те саме правило й pk профілю) — лише `core/access_preview.py`: `preview` (свіжий об'єкт людини: меню `admin.site.get_app_list` + `has_*_permission` кожної моделі, `module_rows` — реєстр, доступ і звідки, операції, `user_can`, `rag_assistant.access.rights_of`, `PAGES` поза адмінкою), `check_url` (адреса → шари `ModuleAccessMiddleware._check_access` + права моделі за `match.func.model_admin` / назвою маршруту). Даних людини не показує й нічого не виконує від її імені. `AuditableMixin.has_add/change_permission` — операція ролі (`user_has_operation`), як `tabele/admin._mv_has_*`; раніше будь-який співробітник міг змінювати замовлення, товари, клієнтів. Тести: `core/tests_access_preview.py`
13. **Закрито при помилці**: `core.utils.user_has_operation`, `_mv_has_change/add_permission`, `ModuleAccessMiddleware` (немає профілю / помилка) — відмова, а не доступ (суперкористувач перевіряється раніше). Операції ролей — `core/utils.ROLE_OPERATIONS`: модулі ролі без рядка тут — лише перегляд; менеджер — пошта, проєкти, Angebote, календар, робочий час, документи — view / add / change
14. **IP людини** (журнал аудиту, «Дозволені IP-адреси» ключів API — `api/key_limits.client_ip` бере те саме) — лише `core.utils.client_ip`: заголовки X-Real-IP / останній X-Forwarded-For — лише коли REMOTE_ADDR у `settings.TRUSTED_PROXIES` (env `MINERVA_TRUSTED_PROXIES`, за замовчуванням локальні й приватні мережі: DSM-проксі на NAS і Docker), інакше REMOTE_ADDR; перший елемент X-Forwarded-For клієнт може підробити. Тести безпеки: `core/tests_security.py`, `core/tests_permissions.py`
15. **/media/ — лише з перевіркою доступу** (`tabele/media.py`, маршрут у `tabele/urls.py`): публічні лише `PUBLIC` (фото / даташити товарів, мініатюри, файли для сайту, логотип — їх відкривають сайт і листи-сповіщення); решта — активний співробітник (без входу — сторінка входу), теки `MODULES` — з доступом до розділу (`user.has_module_perms`), `email_attachments/<скринька>/` — лише власник скриньки (і адміністратор — ні), `knowledge*/` — лише адміністратор (іншим — `/rag/knowledge/<pk>/`); HTML / SVG / XML / JS — завжди `attachment` + `Content-Security-Policy: sandbox`, усім файлам `nosniff`. Нова тека в MEDIA — вирішити, публічна вона чи якого розділу. Тести: `core/tests_media.py`

## 🐛 Відомі проблеми та рішення

| Проблема | Рішення |
|---------|---------|
| CSRF помилка | Додати домен в `CSRF_TRUSTED_ORIGINS` у `settings.py` |
| БД порожня після restart | `docker-compose down` БЕЗ `-v` |
| Міграції конфліктують | `migrate <app> <номер> --fake` → `migrate` |
| Нова БД з нуля | `migrate` без `--fake` (PostgreSQL і SQLite). Міграцію, яку вже пройшли робочі бази, правити лише так, щоб опис моделей не змінився (`SeparateDatabaseAndState`, як sales 0009 / inventory 0022); запобіжник — `core/tests_migrations.py` |
| Static files 404 | `python manage.py collectstatic` або `DJANGO_DEBUG=1` |
| `relation does not exist` | Placeholder app — override `get_urls()`, не викликати `changelist_view` |
| Edit tool "File has not been read" | Спочатку Read потрібного offset, потім Edit |
| `collectstatic` падає в Docker | Прибрати з startup command, використовувати `runserver` з `DEBUG=1` |
